# CPU/GPU и ход ИИ — 18 ноября 2026

Клиентские исходники Orbstrike 0.4.5, Linux. Измерения и независимая
проверка — Sol high. Проверяется гипотеза из третьего пункта таблицы:
«Слабая графика почти не помогает». Само совпадение FPS при LOW/HIGH
не означает ограничения процессором: тесты обязаны оставаться под 60 FPS.

## Как читать метрики

- Интервал `process_frame` — прошедшее реальное время, включая ограничитель
  частоты, синхронизацию и ожидания. Это не занятое время CPU.
- `Performance.TIME_PROCESS` и `TIME_PHYSICS_PROCESS` в установленном
  Godot `4.7.2.stable.arch_linux.ed1daf0bf` публикуют максимум за окно около
  секунды. Среднее повторных чтений не становится средним временем кадра.
  `TIME_PROCESS` охватывает обработку idle и рендер/синхронизацию;
  `TIME_PHYSICS_PROCESS` охватывает физический шаг, включая соответствующие
  обработчики и серверы. Их нельзя подписывать как чистое время GDScript.
  [Точный исходник движка](https://github.com/godotengine/godot/blob/ed1daf0bf/main/main.cpp#L4560-L4762).
- Общая обёртка `tools/test_window.gd` вызывает `force_draw(false, delta)`
  из `process_frame`. Её ожидания также находятся внутри process wall time.
  Окно свёрнуто, нефокусируемо, буфер не показывается; это рендер в текстуру,
  без измерения вывода на экран или задержки ввода.
- Viewport CPU render исключает `_process` и другие подсистемы. Для полного
  render CPU нужны времена всех отрисованных viewport и один общий frame
  setup CPU. Для GPU нужны времена всех активных viewport. CPU и GPU могут
  работать одновременно; складывать их в длительность кадра нельзя.
  Тайминги GPU могут запаздывать относительно сценарной метки; короткий пик
  не приписывается конкретному вызову только по соседству в CSV.
  [RenderingServer](https://docs.godotengine.org/en/stable/classes/class_renderingserver.html#class-renderingserver-method-viewport-get-measured-render-time-cpu).
- При лимите 60 FPS драйвер может снижать частоты GPU. Разница GPU времени
  характеризует именно этот режим, а не максимально возможный FPS. Общий
  процент CPU процесса агрегирует потоки и не доказывает насыщения главного
  потока. Показания `nvidia-smi` — редкие внешние отсчёты, не профиль кадра.
- Прямые таймеры синхронных `AIPlayer.choose_*` отделены от постановки:
  ожиданий `await`, движения камеры, полёта и эффектов. В production методы
  вызываются синхронно из `InteractionController`. В частности, отдельная
  пауза перед броском ИИ задаётся `presentation.wait(0.45)`.
  Вложенные inclusive времена нельзя суммировать; служебная запись вложенного
  таймера может входить в длительность внешнего.

## Вывод

Утверждение «Слабая графика почти не помогает» **не подтверждено как общий
вывод о клиенте**. На одном стабильном поле HIGH → LOW → HIGH root GPU
составил 5.543 → 2.535 → 4.695 мс. LOW действительно сокращает работу
рендера, draw calls 376 → 264, primitives 6 487 219 → 1 717 653.
Частота оставалась около установленного потолка 60 FPS; по этому плато
нельзя объявить постоянное ограничение CPU. Главный поток в этих окнах
получал лишь 2.94–3.97 мс активного CPU на выборку кадра.

При этом есть **разовые синхронные задержки ИИ**: один HARD логический
матч дал до 230.598 мс при выборе ворот/броска и 44.865 мс при выборе
способности. Снижение разрешения не уменьшает эти вычисления. Это
подтверждённый адресный кандидат для будущей CPU-оптимизации, а не
объяснение постоянного FPS во всех режимах. Из регулярных callbacks
в данном захвате наиболее затратен CPU-проход GPU cloth, особенно
упаковка треугольников коллайдеров. Переписывание HLOD/FX-пулов или
всей сцены этим измерением не обосновано. В этом аудите игра не менялась.

## Сценарий и исходные данные

Один финальный Linux/Vulkan Forward+ прогон: Godot 4.7.2 ed1daf0bf,
AMD Ryzen 7 7435HS, RTX 4070 Laptop, root 1280×720, VSync выключен,
симуляция 1×, физика 60 Гц. Штатный check.py/wrapper: окно свёрнуто,
нефокусируемо, render-to-texture, максимум 60 FPS. Изолированные settings/XDG.
Настоящий Boot → меню → обычный матч ID 3 (Каменная бухта), seed 777,
шесть арендованных актёров, реальные броски/рост/один бой до стабильной
границы следующего хода. Затем действия остановлены, камера фиксирована;
idle, cloth, shader time остаются живыми. Это **не полный матч** и не
шесть одновременно раскрытых существ на поле: на итоговых кадрах видны два.
Человеческую сторону обслуживает отдельный тестовый бот NORMAL, NPC также
NORMAL. Данные его helper-вызовов отделены от production-вызовов NPC.

Финальный runner: **32/0, exit 0, 147.79 с**, без runtime ошибок/утечек в
engine/console логе. До idle сегментов script profiler уже выключен.
Все семь сегментов: 120 кадров прогрева + 360 выборок, тот же controller
trace и transform камеры. post_draw delta 359 между первой и последней
из 360 выборок; Engine.frames_drawn=0 закономерен для forced offscreen draw,
поэтому не использован как отсутствие отрисовки. Других Godot процессов
в финальных семи окнах `ps` не обнаружил. Это не инвентаризация всей
посторонней нагрузки рабочего стола.

## Устойчивая сцена: разрешение и пресеты

Значения в мс. Active CPU — Linux utime+stime главного потока за окно,
делённые на 360; не wall latency и не сумма всех потоков. Счётчики читаются
через cat с проверкой, CLK_TCK=100. Root render CPU и общий frame setup
показаны суммой только для render CPU, они не прибавляются к active CPU.

| Сегмент | Root GPU mean | Root render CPU + setup mean | Main active CPU/выборку | Wall mean |
|---|---:|---:|---:|---:|
| LOW 100% A | 3.111 | 0.938 | 3.194 | 16.584 |
| LOW 50% A | 3.132 | 0.920 | 3.083 | 16.583 |
| LOW 50% B | 2.402 | 0.939 | 3.083 | 16.584 |
| LOW 100% B | 2.841 | 0.906 | 3.028 | 16.583 |
| HIGH A | 5.543 | 1.327 | 3.972 | 16.584 |
| Штатный LOW 75% | 2.535 | 0.893 | 2.944 | 16.584 |
| HIGH B | 4.695 | 1.340 | 3.972 | 16.584 |

LOW 100/50 ABBA даёт неоднозначный размер выигрыша: средние двух окон
2.976/2.767 мс, первое 50% окно медленнее первого 100%. При 60 FPS
зафиксированы разные частоты GPU (например, 495–1455 МГц в LOW и
1305–2190 МГц в HIGH в редких замерах границ). Это совместимо с DVFS и
изменчивостью нагрузки, поэтому проценты масштабирования от уменьшения
пикселей не установлены. HIGH/LOW/HIGH, напротив, показывает заметное
сокращение GPU-работы LOW в обоих направлениях. Main active CPU также
снижается, однако его абсолютное время далеко от бюджета 16.67 мс.
Всем окнам свойственна погрешность cap/timer; доля wall >16.667 мс
безопасно не трактуется как пропущенные кадры. Root GPU p95 в HIGH
6.606/6.070 мс; это запас в данном root viewport, не обещание всей GPU.

В инвентаризации были root, два портрета, preview команды и loading viewport.
Сумма в JSON намеренно включает только root + UPDATE_ALWAYS; портреты
UPDATE_ONCE и выключенные viewport сохраняют прошлые readout, поэтому
не складываются. Здесь эта сумма совпадает с root. Работа viewport по
запросу может быть пропущена; это **не исчерпывающий whole-GPU профиль**.

Независимо осмотрены все семь PNG: положение камеры, карты и HUD те же,
позы idle различаются, 50/75% делают 3D мягче, двумерные карты руки остаются
чёткими. Побайтное равенство кадров не требуется и не заявляется.

## Реальные обработчики: штатный script profiler

Внешний TCP collector подключён только к этому тестовому процессу по
127.0.0.1:6037. По маркерам `actions-begin/end` он включает/выключает
штатный `profiler:servers`, максимум 512 функций на кадр, native-call
detail выключен. Production callback не заменяется и не вызывается вручную.
Записаны **2894 кадра, 940 сигнатур, один profile_total**, максимум 386
функций в одном кадре; явного усечения по лимиту 512 не наблюдалось.
Метрики объединяют все экземпляры одной сигнатуры. Доставка команды
асинхронна: первые action кадры до включения могут отсутствовать, последние
кадры захвата могут пересечь границу маркера.

**Один кадр границы enable исключён из таблицы**, исходная запись сохранена:
frame 258 при wall 70.039 мс ошибочно приписывает SlotState.clone 38.646 с.
Это невозможная атрибуция начального перехода profiler, не повод обвинять
clone в 38-секундном зависании. Таблица использует остальные 2893 кадра.
Профилирование само добавляет работу; длительности — elapsed profiler,
включая возможное вытеснение/блокирующие native вызовы, не чистые циклы CPU.
Их нельзя подменять uninstrumented active CPU из предыдущей таблицы.

`total` включает дочерние вызовы. Медиана ниже вычислена **по кадрам, где
сигнатура была записана**, с суммой её экземпляров; среднее делится на все
2893 кадра. Отсутствие записи не объявляется доказательством нулевой работы.

## Синхронные решения ИИ

Во время графического action capture реальный NPC NORMAL вызывал
choose_setup дважды (max 32.908 мс), choose_throw один раз (0.679 мс),
choose_attach один раз (3.030 мс), choose_ability трижды (max 0.621 мс).
Методы вложены: should_open_gate может вызываться внутри оценки и записан
несколько раз; их spans не суммируются. Это instrumented action phase,
не время всего хода. Тестовый бот человеческой стороны имел другие
вызовы (включая setup max 109.624 мс); они не выданы за NPC или человека.

Отдельно выполнен один headless логический HARD/HARD матч текущих
MatchController/AIPlayer, seed 777, 32 шага, 14 ходов, knockout, 28 внешних
решений, exit 0, failures []. Выбранные легальные ворота передаются как
точное приземление: физика, сцена, эффекты и await не симулируются.
Внешние таймеры не включают создание view/legal и запись metadata;
вложенные public calls обходят таймер, добавляя лишь guard. Поэтому это
синхронная wall latency алгоритма с возможным вытеснением планировщиком.

| HARD метод | n | Медиана, мс | Максимум, мс |
|---|---:|---:|---:|
| choose_setup | 8 | 53.5875 | 230.598 |
| choose_ability | 7 | 32.045 | 44.865 |
| choose_attach | 8 | 0.008 | 0.014 |
| choose_ability_target | 3 | 0.008 | 0.009 |
| should_open_gate | 2 | 0.4005 | 0.511 |

Обычного choose_throw в этом логическом матче не было: восемь бросков
выполнены через throw_with_gate. Максимум setup — первое решение при
3/3 живых и 3/3 способностях; максимум ability — ход 11, 4 legal карты,
своя/чужая рука 4/5, живых 2/3. Полные команды/колоды/RNG контекст сохранены.
HARD и NORMAL имеют разные состояния и режимы инструмента: это не A/B
измерение сложности. Отдельные 32–230 мс превышают бюджет кадра 16.67 мс,
однако не устанавливают худший случай или частоту задержек во всех матчах.

## Воспроизведение и независимая сверка

Сначала, в отдельном терминале, запустить listener; затем единственный
графический тест. Нужен текущий графический сеанс. Никаких параллельных
игровых/тяжёлых тестов; чужие процессы не останавливать.

```sh
python docs/audits/2026-11-18-cpu-gpu-limit/script_profiler.py --port 6037 --out build/checks/match-bottleneck-profiler-20261118
ORBSTRIKE_BENCH_DEBUG_PORT=6037 python tools/check.py --profile presentation --checks match-bottleneck
python docs/audits/2026-11-18-cpu-gpu-limit/summarize_profiler.py build/checks/match-bottleneck-profiler-20261118
```

Новый запуск перезаписывает стандартные каталоги; сначала сохранять старые
артефакты. Кодек collector перекрёстно проверен установленным Godot на
сериализации команды и frame пакета, без игрового проекта/рендера.
Независимый Sol high пересчитал все 7×360 root GPU mean из raw,
сверил 11 итоговых SHA исходников и семь production SHA CPU probe,
количества/максимумы AI, границы таймеров, семь PNG и runner логи.
Точные хэши артефактов — [review manifest](review-manifest.json).

Первый графический attempt сохранён отдельно и **не используется** для
финального выигрыша: параллельно работали editor и другой клиент, а чтение
zero-sized `/proc` через FileAccess давало ложный ноль CPU. В финальном
инструменте чтение исправлено и проверено; второй запуск обоснован этими
дефектами методики, успешный тест не повторяли без причины.
[Первый attempt](../../../build/checks/presentation/match-bottleneck-attempt1-20261118/).

Остаются открыты: Windows/слабое оборудование, другие арены/ракурсы,
шесть раскрытых существ на каждом пресете, отдельные полные распределения
по каждой фазе (рост/бой), серия матчей и память. Текущий захват включает
эти действия, но не полный набор контекстов. Сервер, EXE/PCK, сборка,
публикация и прослушивание не выполнялись; опубликованный 0.4.5 не обновлён.
